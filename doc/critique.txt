*critique.txt*  Code review in Neovim: your AI agent's changes, and GitHub PRs

                                                    *critique* *critique.nvim*

critique.nvim reviews code inside your normal Neovim, with a GitHub-style
diff drawn over the real files, so your LSP, telescope, `gd`, grep, and
formatters all keep working. It reviews two kinds of changes:

- GitHub pull requests: the PR is checked out locally, and comments sync to
  a pending review on GitHub as you save them.
- Local reviews with an AI agent (|critique-local|): the agent hands you its
  changes, you comment, it answers and fixes in the same threads, and you take
  turns. Everything stays in the repo, nothing goes to GitHub.

==============================================================================
1. Requirements                                        *critique-requirements*

- Neovim 0.11+
- git
- For GitHub PRs: GitHub CLI (https://cli.github.com), logged in: >sh
    gh auth login
<
  For GitHub Enterprise Server, log in to your company's host: >sh
    gh auth login --hostname github.yourcompany.com
<
critique uses `gh` for everything: fetching the PR, cloning private repos,
and posting comments. There is no setup() call and nothing to configure.

==============================================================================
2. Quick start                                           *critique-quickstart*

From the shell, with the `critique` launcher on your PATH (see the README): >sh
    critique https://github.com/owner/repo/pull/123
<
Or from inside Neovim: >vim
    :Critique open https://github.com/owner/repo/pull/123
<
Then:
1. Move between changed files with the quickfix list (`:cnext`, `:cprev`), and
   between changes in a file with `]c` / `[c`.
2. On a line, `:Critique comment`, write below the ▼ line, `:w`, `:q`.
3. When done, `:Critique submit`.

Until you submit, comments are a pending review: saved on GitHub, visible
only to you. Quit any time and run the same command to continue.

==============================================================================
3. Commands                                     *:Critique* *critique-commands*

:Critique open {url}                                         *:Critique-open*
    Fetch the PR, check it out in a worktree, set the working directory
    there, and show the diff. Any PR link works, including links to a file,
    line, or comment copied from GitHub; critique jumps there: >
      .../pull/123/changes#diff-<hash>R31     line 31 of that file
      .../pull/123/files#diff-<hash>L12       line 12 of the old version
      .../pull/123#discussion_r<id>           that review comment
<
:Critique open {handle}
:Critique open
    Open a local review (|critique-local|) by its handle, e.g.
    `cart-minimum-3f9a`, `cart-minimum-3f9a#3` (jump to thread 3), or
    `cart-minimum-3f9a@/path/to/checkout`. With no argument: the open review
    in the current repo, a choice if there are several, or a new review of
    the current branch's changes if there are none.
:Critique comment                                         *:Critique-comment*
    Comment on the cursor line. If the line already has a thread, open it
    instead, to read it and reply, or to edit your pending comment.
    See |critique-comments|.

:{range}Critique comment
    Comment on several lines, e.g. after selecting them in Visual mode.
    Always starts a new thread.

:Critique delete                                           *:Critique-delete*
    Delete one of your comments on the cursor line. Asks which one.

:Critique resolve                                         *:Critique-resolve*
    Resolve the thread on the cursor line, or unresolve it if resolved.

:Critique before                                           *:Critique-before*
    Show the file as it was before the PR, at the matching line. Comment
    here to comment on deleted lines.

:Critique after                                             *:Critique-after*
    Back to the PR's version of the file.

:Critique toggle                                           *:Critique-toggle*
    Hide or show the diff overlay (|critique-overlay|).

:[range]Critique link                                        *:Critique-link*
    Copy a permalink to the cursor line, or to the lines in [range].
    See |critique-links|.

:Critique files                                             *:Critique-files*
    Reopen the quickfix list of changed files.

:Critique refresh                                         *:Critique-refresh*
    Reload comments. In a local review, also recompute the diff and reload
    files the agent changed (this also happens on its own when it submits).

:Critique submit                                           *:Critique-submit*
    GitHub: publish your pending review as Comment, Approve, or Request
    changes, with an optional summary. Local review: publish your comments to
    the agent with an optional summary; it is then the agent's turn.

:Critique live                                               *:Critique-live*
    Local reviews: turn live mode on or off. In live mode each comment goes
    to the agent when you save it, instead of waiting for :Critique submit.
    See |critique-live|.

:Critique help                                               *:Critique-help*
    Open this help.

                                                               *critique-]c*
]c  [c      In a changed file, jump to the next / previous change.

critique sets no other mappings. Some suggestions: >lua
    vim.keymap.set({ 'n', 'x' }, '<leader>cc', ':Critique comment<cr>')
    vim.keymap.set({ 'n', 'x' }, '<leader>cl', ':Critique link<cr>')
    vim.keymap.set('n', '<leader>ct', '<cmd>Critique toggle<cr>')
    vim.keymap.set('n', '<leader>cs', '<cmd>Critique submit<cr>')
<

4. Comment buffers                                         *critique-comments*

`:Critique comment` opens a markdown buffer in a split. It shows the thread
so far, then a line:
    <!-- ▼ write below · :w saves to your pending review · :q closes ▼ -->
Write your comment below it. `:w` saves it to your pending review on GitHub
(in a local review: a draft the agent sees after `:Critique submit`); saving
again updates the same comment. `:q` closes the buffer.

On GitHub PRs, you can only comment on lines inside a diff hunk: changed
lines plus up to 3 lines of context around them. Their line numbers are
tinted (|hl-CritiqueHunk|). Local reviews allow any line of any file. To
comment on a deleted line, use `:Critique before`.

Comments are placed by line number, so `:Critique comment` refuses while the
buffer has unsaved edits.

==============================================================================
5. The diff overlay                                         *critique-overlay*

On the PR's version of a file:
- added lines have a green background and a `+` sign
- deleted lines appear as red virtual lines above where they were
- within a changed line, the changed words are a darker shade
- line numbers you can comment on are tinted gray-blue
- threads appear at the end of their line: 💬 (✓ when resolved), then in a
  local review the thread number, then the comment count and the first
  comment, e.g. ` 💬 #2 (3) · claude: …`. Your unsubmitted comments use
  |hl-CritiquePending|. A local thread whose code is gone is marked
  `outdated` and stays where the code was.

`:Critique before` shows the reverse: deletions in place, additions virtual.
The buffer is always the real file, so other plugins see the real file.

In a local review, files that have threads but no changes are listed in the
quickfix list too (e.g. `README.md  1 thread`).

==============================================================================
6. Links                                                      *critique-links*

`:Critique link` builds a permalink: >
    https://<host>/<owner>/<repo>/blob/<commit>/<path>#L<n>
<
The host comes from the PR URL, so self-hosted GitHub needs no setup. The
link points at the commit you are looking at: the PR head, or in
`:Critique before` the base commit (and the file's old path if it was
renamed). It works for any file in the repo, not only files in the PR.

The link goes to the system clipboard (|quoteplus|) and the unnamed register.
Without a clipboard provider, it goes to the unnamed register only.

7. Highlights                                            *critique-highlights*

The defaults are GitHub's diff colors, picked for 'background'. Override any
group in your config, e.g. >lua
    vim.api.nvim_set_hl(0, 'CritiqueHunk', { fg = '#7a88a8', bg = '#262a38' })
<
*hl-CritiqueAdd*          Added lines
*hl-CritiqueAddWord*      Changed words within added lines
*hl-CritiqueAddSign*      The `+` sign
*hl-CritiqueDelete*       Deleted lines
*hl-CritiqueDeleteWord*   Changed words within deleted lines
*hl-CritiqueDeleteSign*   The `-` sign (in `:Critique before`)
*hl-CritiqueHunk*         Line numbers of lines you can comment on
*hl-CritiqueThread*       Open threads
*hl-CritiquePending*      Threads containing your pending comments
*hl-CritiqueResolved*     Resolved threads

8. How it works                                           *critique-internals*

- Each repo is cloned once, blobless, to
  `~/.cache/nvim/critique/<host>/<owner>/<repo>/repo.git`, and each PR gets a
  git worktree next to it at `.../pr-<number>`. Reopening fetches new commits
  and checks out the PR head; if you edited files in the worktree, the
  checkout refuses instead of overwriting them.
- The diff is `git diff <merge-base> <head>` with GitHub's settings: 3 lines
  of context, rename detection, Myers algorithm. Your git config can't change
  the hunks.
- Comments go through GitHub's GraphQL API via `gh api graphql`.
- Loads up to 100 threads per PR and 100 comments per thread. Outdated
  threads (on code that has since changed) are hidden, as on GitHub's Files
  tab.

9. Troubleshooting                                   *critique-troubleshooting*

"gh auth login" / HTTP 401 ~
    Run `gh auth login`, or `gh auth login --hostname <host>` for a company
    GitHub.

"GitHub only accepts comments on lines inside one diff hunk" ~
    Comment on a line with a tinted number. For deleted lines, use
    `:Critique before`.

"save or undo your edits first" ~
    Undo (`u`) or reload (`:e!`), so line numbers match the PR.

Reopening fails with a checkout error ~
    You changed files in the worktree. In
    `~/.cache/nvim/critique/<host>/<owner>/<repo>/pr-<n>`, run `git stash`
    or `git checkout .`.

LSP errors about missing dependencies ~
    The worktree is a fresh checkout. Install the project's dependencies
    there, as for any clone.

Disk space ~
    Delete `~/.cache/nvim/critique`, or one `<host>/<owner>/<repo>` in it.

10. Local reviews with an agent                              *critique-local*

A local review is a GitHub-style review of changes in a checkout on your
machine, usually an AI agent's. You review in Neovim; the agent uses the
`critique` shell command. You take turns: each side writes comments, then
submits to hand the turn over. Nothing goes to GitHub.

The loop ~
1. The agent runs `critique start`, makes its change, runs `critique submit`,
   and gives you the command it printed, e.g. `critique cart-minimum-3f9a`.
2. You run it (or `:Critique open cart-minimum-3f9a`). Comment, reply,
   resolve, and delete exactly as on a PR, on any line. `:w` saves a draft
   that the agent can't see yet.
3. `:Critique submit` publishes your comments to the agent.
4. The agent, blocked in `critique wait`, reads them, changes code, replies,
   resolves what it fixed, and submits. Neovim reloads the changed files and
   threads, and says it's your turn.
5. Repeat until you submit with nothing left open.

Agents learn this from the critique skill. See the README for installing it
in Claude Code, Codex, Cursor, and other agents. `critique -h` lists the
shell commands: start, ls, status, list, show, diff, comment, reply,
resolve, unresolve, edit, delete, submit, wait, watch, ack, close.

You can also start a review yourself: `critique` (or `:Critique open`) in a
repo with no review opens a new one of the branch's changes.

Agent-friendly CLI ~
The shell commands print plain text written for agents: each thread with its
code, `needs your reply` on threads waiting for the agent, `new` on comments
since its last submit, and a `Next:` line saying what to do. `list`, `show`,
and `wait` also print JSON with `--json`. `wait` refuses while the agent has
unsubmitted work. Outside a terminal, `critique` never opens Neovim, and it
never writes into the repo except under `.critique/`, so it is safe in agent
sandboxes. `critique diff` prints the changes under review.

Live reviews ~
                                                              *critique-live*
In a live review (`critique start --live`, or |:Critique-live|), your comments
reach the agent as you save them, and its replies and resolves reach you as
it writes them. The agent starts once you've stopped saving comments for
about 20 seconds (its `--settle`), so related comments arrive together;
until then the thread shows `· sent`. When it starts on a thread it runs
`critique ack`, and the thread shows `⏳ <agent> is on it` until it replies.
Neovim tells you what it did: "claude replied on #2, resolved #2". Replying
to a resolved thread reopens it. `:Critique submit` is optional and says
"that's all for now".

The agent has to be listening: `critique wait` (in a live review it returns
as soon as a comment needs the agent) or `critique watch` (a stream). In
Claude Code it listens in the background. If it has stopped, tell it "watch
my critique comments".

Handles ~
Each review has an id such as `cart-minimum-3f9a`. `critique <id>` finds it
from any directory, through an index in your state directory. If the agent's
sandbox could not write the index, its handle is `<id>@<checkout>`. Add `#n`
to jump to thread n. `critique ls` lists open reviews in the current repo.

How it works ~
- Reviews are append-only logs in `.critique/reviews/<id>.jsonl` in the
  checkout. `.critique/` ignores itself, so it never shows up in git.
- The diff is the review's base commit, fixed when it started, against the
  working tree, including uncommitted and untracked files.
- Each comment stores the code it was left on. As the agent edits, threads
  follow that code; if it is gone, the thread is marked outdated and stays
  where the code was, so you can still read and answer it.
- Several agents: give each one its own git worktree. Agents sharing one
  checkout can limit a review to some paths with `critique start --scope`.
